USB DEBUG MONITOR / FACTORY PROTOCOL: promising but not complete execution route
- adml_usb_dev_enable_dbgmon string 0x4b3af2 maps through literal at 0x1fbe4 to function 0x1fa44. It calls 0x94448, which logs PRINTER DEV ENABLE and sets runtime [0x7114e8+1]=1. This enables a printer-device flag; USB descriptor change itself not established.
- adml_module_dbgmon_enable (string0x4b1d5d; reference0x71ac) associated function0x6f6c appears to log and return0; do NOT assume every debug-enable name denotes an operative implementation.
- Function0x6438 logs Enable DBGmon interface and dispatches message/event5 through0x2cb38.
- NEW_CP1_printer_dbgmon__command_parse (string0x4bd20d, pointer0x99758) function0x995c8 checks command bytes: byte0=0x2b, byte1=1, bytes2/3=0, words at+4 and+8=0. Successful match sets result0 and consumes12 bytes. This is a specific packet recognizer, not a shell command.

Combined with event5 enable dispatch above this is a plausible debug-enable route, but callback registration/transport framing/complete path not yet proven. Do not transmit based solely on these bytes.
- Factory/inspection parser names include EC3x_printer_line_inspection__command_parse (0x4bc934, pointer ref0x97ab4), develop, mecha_develop, pwm, lf_write and ud_write. Presence established; exact commands and authorization/mode gates not fully traced.

- 'HDebugWriteMem.. MI fail' exists in main0x2a2389 and boot0xd6cd. It suggests a debugger memory-write handler, but parsing, address checks, invocation path and execute primitive have NOT been established.

ADB
- Case-insensitive whole-word adb, Android, CNXN and WRTE scans found zero matches in main.bin. Four 'adbd' byte substrings are in data/font-like areas, not daemon names or an identified ADB implementation.
- Together with ThreadX context this yields NO evidence for Android ADB. It is a bounded negative result, not proof no proprietary debug protocol exists.

CUSTOM PROGRAM PATH ASSESSMENT
- Telnet login alone does not provide an execution primitive; discovered commands are diagnostic iperf.
- Most useful next static target is printer dbgmon event5 -> callback registration -> actual USB/debug monitor command dispatcher -> memory read/write/execute handlers and mode gates.
- Need establish RAM map, calling convention, cache handling and safe entry point before a RAM-only test payload can be justified. No ready-to-run loader or unsigned firmware acceptance demonstrated here.
