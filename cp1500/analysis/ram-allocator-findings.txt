ALIGNMENT / LIFETIME / CONTEXT
- Underlying region allocator320d98 sets minimum payload8 bytes, rounds requested length to4, adds8 bytes internal header; no evidence of guaranteed8/16/32/64-byte payload alignment. Only4-byte alignment can be claimed.
- If payload needs stronger alignment, request extra bytes, keep original pointer for free; payload alignment does not make its address an allocator base.
- Global arena allocation/free uses lock functions2d6360/2d63b8.31df18 also invokes registered reclaim callbacks on allocation failure and retries. These APIs are not established safe from interrupts, while the monitor halts the owner task, or with allocator lock already held.
- Allocation is uninitialized data; no implicit zeroing observed in simple malloc. Capacity and live free bytes depend on runtime state. No fixed payload address is available statically.
- Ownership ends when matching free is called or firmware resets/reinitializes pools. Do not mix malloc/free with DMB handles or ThreadX block APIs.
- Code execution from returned cached buffer additionally requires instruction/data cache coherence and valid calling context; allocator alone does not establish either.

OPEN ITEMS
- Exact initialized heap region(s)/capacity and runtime free bytes require following rammgr registration and/or reading live metadata.
- DMB allocate/free/accessor APIs not fully recovered here; no recommendation to use them instead of established global malloc/free.
- Safe monitor-side invocation context, allocator ownership during callbacks, and cache maintenance must be resolved before using any of these routines on hardware.
