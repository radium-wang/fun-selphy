RESPONSE / FLOW CONTROL
0x2a2314 queues8-byte command reply in128-entry per-channel ring.
0x2a24cc builds output submessages. Not all commands return the same shape:
memory-read commands may append data, setter/write commands may have only6-byte
subheader. Do not assume a single synchronous8-byte acknowledgement per request.
Subheader byte4 grants credit; channel credit tracked at table+4.
Outer checksum and active-channel exchange are mandatory protocol layers;
see transport report. This document is not a ready-to-send host client.

FUNCTION CALL C (0x43): REAL CALL, NOT PROVEN ARBITRARY GO
RX dispatcher0x2a24a8 calls0x2a1ab8. It obtains a0x404-byte pool block, reads
LE16(command+4) body bytes from FIFO into the block, then calls symbol lookup
0x2e0994. Lookup compares the body-start string to exported names and returns
record type, size and pointer. Only type==6 is accepted (0x2a1b44..50).
0x2a1b64 BLX r3 calls the returned record+0x18 function pointer, with
r0=request block, r1=request length, r2=request block+0x400 response area.
This is a registered extension-command ABI, not an address field GO command.
TX helper0x2a1ba8 reads response length at block+0x400; pooled block is released.
There is no demonstrated cache invalidation or arbitrary executable-loading ABI.

ASSESSMENT
RAM read/write: high-confidence implemented and wired to DBGmon mux.
Loading custom bytes into RAM: supported by the same write primitive in code;
not demonstrated on hardware, and usable allocation must first be established.
Executing those bytes: unresolved. Existing C command is symbol/type gated.
Writable callbacks/symbols suggest possible further avenues, but no such bypass,
function-pointer alteration, or execution experiment was performed or validated.
Next useful hardware evidence would be USB debug enumeration and a read-only
known-byte comparison; then separately allocated-RAM round-trip verification.
Running code additionally needs a proven entry, ABI, cache and scheduler handling.
