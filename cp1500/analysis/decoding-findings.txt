CP1500 字节编码与启动解压流程分析
日期：2026-10-30（Asia/Shanghai）

结论
已恢复固定的 256 字节替换表，并用它成功提取 1.0.6.0、1.0.7.0 的启动程序和 gzip 主程序。
两版主程序解压结果均为 7,724,800 字节，gzip CRC32、ISIZE 和数据消费长度全部验证通过。
本结果来自本地 Python / Capstone 静态分析，不是 REA Evidence；没有运行固件或操作打印机。

一、编码规律
以输入字节作为索引，从以下表中取输出字节：
  [00] + [FF, EE, DD, CC, BB, AA, 99, 88, 77, 66, 55, 44, 33, 22, 11]
       + [FE..01 倒序，排除所有 0x11 的倍数]
即 Python：
  table = bytes([0] + list(range(255, 0, -17))
                + [x for x in range(255, 0, -1) if x % 17])
  decoded = raw.translate(table)
示例：编码 00 -> 00；01 -> FF；09 -> 77 ('w')；0A -> 66 ('f')；A0 -> 65 ('e')；E1 -> 20（空格）。
这是一一对应、可逆的固定字节替换，不需要秘密密钥。
适用范围：所提取的启动程序和压缩主程序已经独立验证。文件中也有未经编码的字段，例如
0xA0000 的原始 OART 标记和文件尾版本字符串；不能把整文件统一转换后的视图当成可刷镜像。

二、前 640 KiB 的结构
原始文件偏移（编码还原不改变长度）：
- 0x000000：数值 374（0x176）及其 32 位按位反码。
- 0x000008：374 个 5 字节记录；形态类似 32 位寄存器地址 + 8 位设置值，用途为推断。
- 0x000756：0x00500000、0x0002F2C0、0xFFFD0D3F；后两者互为反码。
- 0x000762：启动程序本体，长度 193216（0x2F2C0）字节。
- 0x02FA22：0x005000DC 及其反码；与启动程序中的 ARM 函数入口吻合，解释为入口候选。
- 后续大量填充：原始 0x0B 还原为 0x55，原始 0x01 还原为 0xFF。
- 启动程序内部出现 OABF、OASN 标记以及 0xA0000 值，后者与 ROM 表位置吻合。

三、前次 10 字节变化的解释
1.0.6.0 原始偏移 0x2AC3E：17:59:37 Nov  8 2024
1.0.7.0 原始偏移 0x2AC3E：22:39:34 Dec 23 2025
两版 193216 字节启动程序逐字节比较，所有差异都在这个时间字符串内，共 10 个字节。
因此本次启动程序没有观察到时间字符串以外的变化；不对整个系统的行为等同性作推断。

四、启动代码与解压流程
以下地址基于头部给出的加载地址 0x00500000；启动程序文件偏移 0 对应该地址。
原始 CNN 偏移 = 地址 - 0x00500000 + 0x762。
- 0x501FF4：加载/元数据处理函数候选，有 ROMTAB、fwz 等日志引用。
- 0x5022DC–0x502334：所检查的路径按 32 位字读入、异或累积，最后与 0 比较。
  失败分支输出 ROM Checksum Error。该局部校验不能证明升级包没有其他签名验证。
- 0x5024C8：应用加载/解压包装函数，引用 Inflate Application。
- 0x50254C–0x50255C：屏蔽输入字的最高 8 位，再与 0x00088B1F 比较，即 gzip 前三个字节。
- 0x502578：调用 0x502FD8 初始化解压状态。
- 0x502584：调用 0x502CD4 执行解压；随后核对返回长度与期望长度。
- 0x502FD8：状态初始化；源指针加 10，符合跳过这里的 gzip 固定头。
- 0x502CD4：解压状态机；可见读取 1 位、2 位及处理存储块长度的路径，与 DEFLATE 相符。
  离线 zlib 成功解压并验证 CRC 是额外独立佐证。
尚未定位执行“外层字节替换”的设备侧函数；它可能在其他镜像/更新处理路径中，未作结论。

五、ROM 表与主程序
原始 0xA0000 处的 OART 为明文标记；其后解析出的字段包含：
- +0x0C：98 项；+0x1C：原始固件总长度（两版均匹配）。
- +0x28：98 项、每项 12 字节的表，三个字段是地址、长度、标志（语义由边界验证推断）。
- 地址减去 0x80000000 可得到本文件偏移；全部 98 项均通过文件边界检查。
- 表长度 0x28 + 98*12 = 0x4C0，与表内自己的区段长度匹配。
- 第 6 项（从 0 计数）标志为 1，地址 0x800A0CC8；指向 gzip 主程序。

1.0.6.0：gzip 原始偏移 0xA0CC8，压缩长度 4162554，解压长度 7724800，CRC32 5676FFCD。
1.0.7.0：gzip 原始偏移 0xA0CC8，压缩长度 4163165，解压长度 7724800，CRC32 FAB33C1E。
两版解压都完整消费表内指定的压缩区间，无剩余输入，且 CRC32/ISIZE 相符。
主程序包含连续 ARM 指令、Canon SELPHY CP1500 字符串、网络配置网页等。
启动程序和主程序均含 ThreadX ARM9/RVDS Version G5.8.5.4 标识。
ARM 指令及字符串支持 ARM/ThreadX 判断，具体芯片型号仍未确认。

六、产物与复现
python3 cp1500/unpack_cnn.py
仅依赖 Python 标准库；读取 original 中的两个 CNN，不修改原文件。
输出 unpacked/1060 和 unpacked/1070，各包含：
- prefix-640KiB.decoded.bin：还原的前 640 KiB
- boot.bin：启动程序
- main.gz：还原字节编码后的原始 gzip 数据
- main.bin：校验通过的主程序
- boot.strings.txt / main.strings.txt：静态字符串及对应输出文件偏移
- manifest.json：源哈希、输出哈希、替换表、ROM 表、校验和推导边界

反汇编脚本：inspect_boot.py（项目内 tools-python 的 Capstone 5.0.6）
反汇编证据：analysis/boot-loader-checksum.asm、analysis/boot-inflate.asm。
REA 的 Ghidra 未配置、Hopper 不存在，因此本次没有 REA 原生反编译结果。
反汇编包含线性扫描的数据区，数据可能显示成伪指令；本文函数结论只依据连续代码和实际调用链。

限制
已经解决字节编码和所识别主程序的解压；尚未建立完整重新打包、签名校验或设备接受机制。
可逆编码及 gzip CRC 通过不等于修改后的固件能刷入或启动。
